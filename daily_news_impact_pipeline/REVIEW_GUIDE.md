# Reviewer Guide

This guide is for readers who want to understand the project quickly without needing access to the production database, private API keys, or local crawler credentials.

The repository is a public engineering showcase for a daily financial news impact agent. It exposes the architecture, orchestration code, prompt contracts, wiki build design, and curated execution artifacts.

## What Requires The Production Environment

The public repo intentionally leaves some production dependencies behind adapter boundaries:

- live crawler credentials and local crawler state
- full local document database
- private LLM provider keys
- internal raw API requests and raw provider responses
- full production `comm_profile.news_impact` runner modules

The visible code still shows how those parts connect:

- `source_update.py` lists the exact crawler/parser/index commands expected by the orchestrator
- `impact.py` defines the policy and disclosure runner boundary
- `force_rebuild.py` contains the reduced rebuild execution path used after a disclosure marks `force_rebuild`
- `examples/` provides representative execution traces after those runners complete

## Key Design Decisions To Review

### 1. Policy News Uses A Matching Branch

Policy news starts without a known ticker. The policy branch therefore uses:

1. source and usability gates
2. optional compression
3. round-1 hybrid search over the final wiki index
4. round-2 company-filtered search over first-round candidates
5. initial match as the expensive narrowing point
6. final impact analysis only for matched companies

Relevant files:

- [`open_source_assets/policy_news_branch_detail.png`](open_source_assets/policy_news_branch_detail.png)
- [`examples/news_impact/policy_matched_energy_carbon/`](examples/news_impact/policy_matched_energy_carbon/)
- [`examples/news_impact/policy_no_initial_match/`](examples/news_impact/policy_no_initial_match/)

### 2. Company Disclosure Uses A Direct Branch

Company disclosures are already mapped to a ticker. The branch skips policy-style RAG matching and runs:

1. source loading
2. length gate and optional compression
3. company-specific impact analysis
4. wiki action decision
5. optional patch or force rebuild after impact is saved

### 3. The LLM Company Wiki Is A First-Class Artifact

The wiki is a compact, evidence-bound company knowledge object. It is designed for retrieval and impact reasoning, not for marketing copy.

The wiki exposes:

- business model and value-chain position
- products, projects, assets, entities, aliases, geographies
- customers, suppliers, counterparties, and uncertainty boundaries
- earnings drivers, balance-sheet pressure, and event sensitivity
- freshness and stale-data boundaries

### 4. Full Wiki Build Agent Is The Deep Research Extension

The daily pipeline uses the reduced builder by default. The full builder is documented as an optional high-budget route for first-time onboarding and manual deep review.

It demonstrates:

- deterministic graph orchestration
- ReAct-style planner subagents inside bounded research loops
- shared evidence banks and mutable research notes
- critic-driven revision
- valuation assumptions converted through strict JSON into deterministic calculators
- final synthesis into a durable LLM company wiki

### 5. Token Saving Is Part Of The Product Design

The pipeline avoids expensive LLM calls when a source is low signal or when no matched company exists.

Examples:

- `policy_no_initial_match` stops before company-by-company final impact
- company disclosures default to `no_update`
- reduced rebuild is deferred and batched after impact analysis

## Suggested Code Review Questions

- Does each expensive LLM node have a clear upstream gate?
- Does each JSON-producing node have a small schema and a bounded role?
- Does the policy branch avoid passing noisy evidence into the final impact node?
- Does the disclosure branch save impact before changing the wiki?
- Does the wiki update logic preserve old versions through archive records?
- Does the reduced wiki builder separate retrieval planning from source evidence?
- Are daily outputs useful without reading raw run directories?

## Suggested Demo Commands

Offline mode:

```powershell
python daily_news_impact_pipeline\show_wiki_build_plan.py --describe-modes
python daily_news_impact_pipeline\show_wiki_build_plan.py --mode reduced --ticker 002796 --company 世嘉科技
python daily_news_impact_pipeline\show_wiki_build_plan.py --mode full --ticker 688668 --company 鼎通科技
```

Dry-run orchestration:

```powershell
python daily_news_impact_pipeline\run_daily_news_impact_one_click.py `
  --date-from 2026-04-25 `
  --date-to 2026-04-28 `
  --run-id review_dry_run `
  --dry-run
```

The dry run writes stage plans without live crawler, database, or LLM calls.
